## 一、架构定稿：两条腿

```
ESP32 ──HTTPS 批量POST──▶ 中转层 ──▶ 自建 TiDB      设备写时序
                                        ▲
                                        │ Skill + HTTP 工具（❌未验证）
                                        │ 或 后端预查询塞进上下文（✅保底）
手机App ──Session/Turn──▶ Agent Stack ──┘
                              └─ mem9 ─▶ Stack 内部 TiDB    长期记忆
```

设备写库，Agent 读库，App 只和 Agent 说话。**设备和 App 互不知道对方存在。**

## 二、必须补的一条边：配置下行

当前设计是**单向的**：设备只往上 POST。但家长端 App 要能改：
每日目标、推荐距离范围、光照下限、提醒冷却时间、提醒方式开关、番茄钟参数。

这些必须下发到设备，否则 App 的「目标与规则」整节都是摆设。

**推荐做法：批量上报的 HTTP 响应里带回当前配置。**

```
POST /ingest  →  { "ok": true, "config": { "daily_goal_s": 14400,
                    "dist_min": 400, "dist_max": 850, "lux_min": 1500,
                    "cooldown_s": 1800, "rev": 7 } }
```

设备比较 `rev`，变了就落盘生效。零额外连接、零额外协议，配置变更在一个上报周期内（30–60 秒）生效。
比 MQTT / WebSocket 简单一个数量级，对 ESP32 也友好。

## 三、特征向量：四个要改的问题

现方案：16 维手工特征 + `VEC_COSINE_DISTANCE`。**手工特征这个思路是对的**——
零模型成本、低维、每维可解释，非常适合这个场景。但具体实现有四个问题。

### 3.1 距离函数选错了 ⚠️

余弦距离衡量的是**向量夹角，与模长无关**。但这里模长就是信号本身：

- A：时长 0.90、过近次数 0.80、弱光 0.70
- B：时长 0.09、过近次数 0.08、弱光 0.07

余弦距离认为 **A 和 B 完全相同**（方向一致），但现实里一个是学了 1.8 小时问题严重的时段，
另一个是学了 11 分钟基本没事的时段。

**建议改用 `VEC_L2_DISTANCE`。** 注意向量索引是绑定距离函数的，要一起改：

```sql
VECTOR INDEX idx_emb ((VEC_L2_DISTANCE(embedding)))
```

现在只有 20 行测试数据，两种都建一遍跑对比很便宜，改动成本几乎为零。

### 3.2 「星期」这一维会压制其他所有维度 ⚠️

现在是原始值 0–6，而其余每一维都归一化到约 0–1。
**星期的数值影响力是其他维度的 6 倍**，检索结果会被「同一天」主导。

而且它是**循环量**：周日(6) 和周一(0) 现实中相邻，数值上却最远。

修法和小时一致，改成 `sin(2πd/7), cos(2πd/7)`。

### 3.3 护眼分和桌宠体力是派生量，不该进向量 ⚠️

这两个值本身就是由距离、光照、时长算出来的。放进向量等于把同样的信号**计入两次**，
人为放大了它们的权重，相似度会被这两维带跑。

它们是**输出**，不是特征。建议移出。

### 3.4 修订后的 16 维

移出 2 个派生量、星期拆成 2 维，正好还是 16：

```
[ 时长/7200, 平均距离/1000, 距离方差/200, 光照百分比/100,
  (左右光差+500)/1000, 过近次数/20, 过近秒数/1800, 弱光秒数/1800,
  打断次数/10, sin(2πh/24), cos(2πh/24), sin(2πd/7), cos(2πd/7),
  温度/40, 湿度/100, 在座占比 ]
```

最后一维换成「在座时长 / 时段总时长」，比派生分数更有信息量。

## 四、光照维度目前接近失效 ❌

**这是硬件实测结论对数据设计的直接影响，必须处理。**

实测：室内常态光照下，两路光敏的 ADC 读数是 **3935 / 3941**（12 位满量程 4095）。
多量程交叉验证确认**不是 ADC 削顶**，是传感器输出本身就在 2.98V，
往上只剩约 160 个计数余量。

对照设备端现有规则：

| 规则 | 阈值 | 实测常态值 | 结论 |
|---|---|---|---|
| 合理亮度范围 | 1500–4050 | 3935 | 贴着上界 |
| 弱光提醒触发 | < 1500 持续 5s | 3935 | **常态下几乎永不触发** |

后果：
1. 「台灯太暗」提醒在真实场景里基本不会响，除非房间真的很黑
2. 特征向量里 `光照百分比` 和 `弱光秒数` 两维**近似常量，贡献接近零**
3. 家长端 App 的「光照不足次数」会长期为 0

**1500 这个阈值目前没有任何实测依据**，是拍出来的。

### 要做的两件事

**a) 加减光片**（物理）：给两路光敏各贴同样厚度的减光片，把常态读数压到 2000 左右，
腾出上行余量。两路必须一致，否则左右差分失去可比性。

**b) 做一次两点标定**（10 分钟，收益极大）：
用手机照度计 App 放在光敏旁边，记录几组「ADC 读数 ↔ lux」，
拟合出 300 lux（国标读写作业面下限）对应的 ADC 值，用它替换 1500。

这一步同时解锁家长端 App 显示**真实照度数值**——
否则按之前的约定只能显示百分比，不能显示 lux。

## 五、数据模型对不上 App 清单的三个缺口

现有四张表覆盖了大部分功能，但这三项没有落点：

| 缺什么 | 支撑的 App 功能 | 建议 |
|---|---|---|
| 桌宠状态（HP / GROW / 形态） | 第七节「桌宠共育」 | 加 `pet_state` 表，或并入 `child_baseline` |
| 设备 / 孩子档案 | 多设备、多孩子切换 | 加 `device` + `child` 表，其余表挂外键 |
| 配置项 | 第五节「目标与规则」全节 | 加 `device_config` 表，带 `rev` 版本号，配合第二节的下行通道 |

`reminder_event` 表是对的——它支撑「提醒响应率」，那是这个 App 最有价值的独有指标。

## 六、对话功能的风险与保底方案 ⚠️

App 清单第四节（AI 周报总结）和第八节（家长提问）都依赖
**Agent 能读到自建 TiDB 的数据**。而这条边现在是未验证的：
Skill 能否调用任意外部 HTTP 工具，文档没写清楚。

**建议：先做保底路径，把 Skill 调 HTTP 当作升级项。**

- **保底（必做）**：后端先按问题查好数据，把结果塞进 Turn 的上下文一起发给 Agent。
  百分百可行，只依赖已验证的 `POST /api/sessions/{id}/turns`。
- **升级（可选）**：Skill 直接调后端 HTTP 查库，Agent 自主决定查什么。更漂亮，但有落空风险。

比赛有 deadline，把会话功能压在一个未验证的能力上风险太大。

## 七、上报频率与免费额度

`sensor_raw` 每 10 秒一条 = 8640 行/天/设备，约 864KB/天、26MB/月。存储完全不是问题。

但**建议云端只存 60 秒聚合，10 秒原始数据留在 SD 卡**：

- 行数直接降到 1/6
- 家长端「学习时间轴」用 60 秒粒度完全够
- 出问题要排查时，SD 卡上有全量原始数据

这样即使免费档 RU 额度紧张也很安全，而且不损失任何 App 功能。
